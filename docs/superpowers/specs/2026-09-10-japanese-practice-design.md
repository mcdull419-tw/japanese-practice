# 日語練習網頁 設計文件

- 日期：2026-09-10
- 教材：大家的日本語（中文版）初級 I / II，`01.pdf` ~ `50.pdf`
- 第一階段內容範圍：第 1 ~ 15 課

---

## 1. 目標

建立一個可從手機與電腦透過瀏覽器使用的日語練習網站，題目來自「大家的日本語」課本素材，具備間隔重複（SRS）能力，會依據使用者對**個別知識點**的掌握程度自動調整出題機率。

三個核心設計立場，其餘設計皆由此推導：

1. **題目是生成的，不是抄的。** 課本內容是素材，題目由生成器從素材產生。
2. **熟悉度掛在「概念」上，不是掛在「題目」上。** 使用者不熟的是「助詞 に 表對象」這個知識點，不是某一道特定題目。
3. **儲存的是複習事件日誌，不是分數快照。** 分數是從日誌算出來的。

## 4. 抽取管線（tools/extract/）

### 4.1 已驗證的事實

以下皆經實測確認，實作時直接採用，不需重新探索：

- 環境無任何 PDF 工具（無 poppler／mutool／pypdf／PyMuPDF）。**以 Python 標準函式庫 `re` + `zlib` 實作**，此路徑已證實可行。
- 內容串流為 FlateDecode。文字以 `<hex> Tj` 與 `[...] TJ` 繪製，`/TTn 1 Tf` 選字型，`a b c d e f Tm` 給出字級（a、d）與座標（e、f）。
- **編碼須由字型物件的 `/Encoding` 判定**，不可寫死字型代號：含 `RKSJ`／`90ms` → `cp932`；含 `GBK`／`GB` → `gb18030`；`WinAnsiEncoding` → `cp1252`。
  - 驗證樣本：`82b182c682ce` → cp932 → `ことば`；`b5daa3b1d56e` → gb18030 → `第１課`。
  - 誤判徵兆：輸出出現 `偼偄偆` 這類罕見漢字，代表把 Shift-JIS 位元組誤用 GB18030 解讀。
- **PDF 內部結構至少有兩種版本**：07/10/12/14/15.pdf 為 PDF 1.3 物件明文；11/13.pdf 為 PDF 1.6，使用壓縮物件流（ObjStm）與交叉參照流，須先解壓物件流才找得到 Pages tree 與 Resources；13.pdf 第一頁的 `/Resources` 為內嵌字典而非間接參照。**尚未驗證全部 50 課，可能還有其他變體。**
- **振假名規則（第 7 課實測）**：ruby 固定為 4.8pt 小字級，y 座標比對應漢字高固定 12.0pt（與漢字本身字級無關）。以固定 y 偏移 ＋ x 最近鄰配對，距離門檻 11pt。第 7 課 416 個 ruby 字符配對成功 412 個（99%）。
  - 注意：多音節對應單一漢字時（`木村` → `きむら`），須將落在同一漢字上的所有假名依 x 排序後**串接**，不可只取第一個。
- **單字表切分**：多數單字的假名與漢字為兩段獨立 TJ 字串；少數（如 `て/手`）為單一字串靠字距 `Tc` 撐開視覺間隔，須以「字串中第一個 CJK 表意文字」為切點。
- **單字的搭配用法子行**（實測缺陷）：部分單字下方有一行方括號註記，如第 7 課第 9 筆 `かけます` 下方的 `［でんわを～］／［電話を～］`。原型將整行遺失，且中文欄的 `〔〕` 角括號被誤過濾。**此子行必須保留為 `vocab[].usage`**——`かけます` 單獨無意義，課本教的是 `電話を かけます`，代入題與挖空題都需要這個搭配。過濾偽漢字欄位時不可連帶刪除含實質內容的角括號。
- **頁首含出處資訊**：每頁頁首右上為 `課:7 (頁:1/9)`，可直接用於 `source_ref` 的頁碼標註。
- **PDF 頁面算繪**：macOS 內建 Swift + PDFKit 即可（`tools/render.swift`，用法 `swift tools/render.swift 07.pdf outdir 2.0 1 9`），不需 poppler，不需 Homebrew。這是抽取結果的視覺驗證手段。

### 4.2 架構約束：中介表示必須保留座標

原型的缺陷全部源自同一個原因——太早把文字壓平成字串，丟失位置資訊。已知受害處：

- 文法解說的日文整段消失（日文與中文交錯排版，只保留了中文字型片段）
- `「で」` 變成空的 `「」`（引號中間的日文是獨立片段，需靠 x 座標插回）
- 練習Ａ 代入表的欄位對齊無法還原
- 練習Ｂ 同列項目順序錯亂（`2) 教えます 1) 貸します →→`）

**因此：抽取分三階段，字串化是最後一步。**

```
階段一  解析 → Fragment[] { text, x, y, size, font, page }
階段二  版面分析 → 行分組 → 欄位偵測 → 區段切分 → ruby 配對
階段三  序列化 → JSON
```

### 4.3 區段切分

每課依序為：`ことば` → `文型` → `例文` → `会話` → `練習Ａ` → `練習Ｂ` → `練習Ｃ` → `問題` → 文法解說。

**已知陷阱**：`会話` 標題出現兩次——第一次是 ことば 頁尾附的會話用語小框，第二次才是對話本文。須以版面位置或字級再細分，不可單純用標題文字偵測。

### 4.4 練習Ａ 代入表 → 句型模板

這是本設計的關鍵資產。課本練習Ａ 本身就是「模板 ＋ 槽位候選詞」，且候選詞由課本編者挑選，語意保證自然。範例（第 7 課練習Ａ-1 原文）：

```
日本人          は  はし                で  ごはんを 食べます。
インドネシア人      スプーンと  フォーク
アメリカ人          ナイフと  フォーク
```

依 x 座標分欄後可還原為：

```yaml
id: L07-A1
template: "{S}は {T}で ごはんを 食べます。"
slots:
  S: [日本人, インドネシア人, アメリカ人]
  T: [はし, スプーンと フォーク, ナイフと フォーク]
rows: [[0,0], [1,1], [2,2]]     # 同列詞彙為一組，不可跨列自由組合
requires_lesson: 7
```

`rows` 欄位很重要：同一列的詞是課本配好的組合（日本人↔はし、アメリカ人↔ナイフとフォーク），**不可跨列亂配**，否則會生出語意荒謬的句子。第 7 課有 6 張這樣的表，第 1 ~ 15 課估計 80 ~ 90 張。

### 4.5 產出格式

```json
{
  "lesson": 7,
  "vocab": [
    {"no": 1, "kana": "きります", "kanji": "切ります", "zh": "剪，切", "usage": null},
    {"no": 3, "kana": "あげます", "kanji": null, "zh": "給，送", "usage": null},
    {"no": 9, "kana": "かけます", "kanji": null, "zh": "打〔電話〕",
     "usage": {"kana": "でんわを～", "kanji": "電話を～"}}
  ],
  "sentences": [
    {"id": "L07-bunkei-1", "section": "文型", "no": 1,
     "jp": "わたしは ワープロで 手紙を 書きます。",
     "ruby": [{"base": "手紙", "kana": "てがみ", "at": 9}],
     "zh": null,
     "alt": []}
  ],
  "patterns": [ /* §4.4 格式 */ ],
  "grammar": [{"no": 1, "title": "名詞（工具／手段）＋で＋動詞",
               "body_zh": "…", "examples": [{"jp": "…", "zh": "…"}]}]
}
```

`ruby[].at` 記錄 base 在 `jp` 中的字元位置，避免同一漢字在句中出現多次時無法定位（例文 1 的 `勉強` 就出現兩次）。

`alt` 收錄課本自己標註的替代形式——例如第 7 課文型 3 的 `もらいました。（から）` 表示 `に` 與 `から` 皆可，直接餵給評分的 `alternatives`。

### 4.6 校對機制

抽取結果須人工抽查。提供 `tools/export_items.py` 匯出全部生成題目為可讀清單；發現的錯誤寫入 `data/corrections.json`（以 item_id 或 vocab no 為鍵），套用於管線輸出之上。**不直接手改 `data/lessons/*.json`**，否則重跑管線會被覆蓋。

### 4.7 補充講義（JPEG）

目錄中 21 張 `IMAG*.jpeg` 為使用者拍攝的補充講義照片（含手寫筆記），內容為數字表、時間、量詞等。含手寫標註，OCR 不可靠，**改以人工轉寫為 `data/supplements/*.json`**，屬 Phase 2 工作。

## 5. 資料模型

三層。素材是課本給的，概念是知識點，題目是兩者的產物。

### 5.1 素材層（Material）

來自 §4.5 的抽取產出：單字、句子、振假名、代入表、文法點。

### 5.2 概念層（Concept）

可被「學會」的最小知識單位。熟悉度真正掛在這裡。

| 類型 | ID 格式 | 例 |
|---|---|---|
| 單字字義 | `w:<lemma>` | `w:okurimasu` |
| 漢字讀音 | `w:<lemma>:reading` | `w:tegami:reading` |
| 動詞分類 | `w:<lemma>:group` | `w:kaerimasu:group`（帰る 是 I 類的例外） |
| 變化規則 | `r:<form>:<group>` | `r:te:group1` |
| 助詞用法 | `p:<particle>:<usage>` | `p:ni:recipient` |
| 句型 | `g:<pattern>` | `g:mou_mashita` |
| 量詞 | `c:<counter>` | `c:hon` |
| 數字規則 | `n:<type>` | `n:time:hour` |

`data/concepts.json` 為**人工維護**的定義檔：

```json
{
  "p:ni:recipient": {
    "label": "助詞 に（動作對象）",
    "skills": ["文法", "助詞"],
    "requires_lesson": 7,
    "source_ref": "第7課 文法3"
  }
}
```

第 1 ~ 15 課估計約 70 個文法／助詞概念，加上單字概念（自動生成，約 900 個）與變化規則（約 20 個）。

**為何文法概念要人工定義而非從 PDF 抽**：文法解說的抽取品質最差（§4.2），而數量只有約 70 個，人工定義既快又精準，且能寫出比課本標題更適合當概念名稱的標籤。

### 5.3 題目層（Item）

```js
{
  id: 'conj:okurimasu:masu→te',   // 決定性，不含隨機成分
  engine: 'transform',
  lesson: 7,                       // 素材出自第幾課
  requires_lesson: 14,             // 需要的最高課次 = max(素材課次, 形態課次)
  covers: ['r:te:group1', 'w:okurimasu:group'],
  skills: ['變化', '動詞'],
  prompt: { type: 'text', text: 'おくります', hint: 'て形' },
  answer: 'おくって',
  alternatives: [],
  source_ref: '第7課 ことば2 ／ 第14課 て形'
}
```

**`id` 決定性是硬性要求。** 題庫重新生成時，同一道題必須得到同一個 ID，否則 SRS 歷史全部失效。ID 由「生成器名 : 素材鍵 : 參數」組成，禁止使用亂數或時間戳。

**`requires_lesson` 是範圍過濾的依據**（需求 #18）。`送ります` 是第 7 課單字，但て形第 14 課才教，所以這道題 `requires_lesson = 14`；使用者把範圍設在 1 ~ 15 時它會出現，設在 1 ~ 10 時不會。

### 5.4 懶生成

生成器**不預先展開成磁碟上的巨大 JSON**。載入時在記憶體中展開（第 1 ~ 15 課估計 3000 ~ 5000 題，展開時間 < 100ms）。好處是新增題型不必重跑建置、資料檔維持精簡。校對需要時再用 §4.6 的指令匯出。

## 6. 題目生成器與引擎

15 項需求收斂成 **4 個引擎 ＋ 1 個呈現修飾 ＋ 1 個播放器**。多數需求的差異在**內容**而非**機制**——給予接受、存在句、比較偏好、希望願望，機制上全都是代入題，只是句型來自不同課次。

### 6.1 四個引擎

| 引擎 | 機制 | 涵蓋需求 | 素材來源 |
|---|---|---|---|
| **recall** 對照題 | 給 X 求 Y，單一答案 | 1, 4, 7 | vocab、numbers、counters |
| **transform** 變換題 | 給一形態求另一形態 | 2, 3 | vocab ＋ `conjugate()` |
| **substitute** 代入題 | 給例句與提示詞，產出完整句 | 6, 8, 9, 10, 11, 13 | patterns（練習Ａ／Ｂ） |
| **cloze** 挖空題 | 句子挖掉成分 | 5, 12 | 任意 sentence |

統一介面（讓多個 subagent 可平行開發，互不衝突）：

```js
// app/generators/<name>.js
export const id = 'transform';
export function* generate(material, scope) { /* yield Item */ }

// app/engines/<name>.js
export const id = 'transform';
export function render(item, host, opts) { /* 產生 DOM，回傳取值函式 */ }
export function grade(input, item) { /* → {correct, grade, diff} */ }
```

引擎彼此不互相 import，只依賴 `core/normalize.js` 與 `core/ruby.js`。

### 6.2 聽力是呈現修飾，不是第五種引擎

需求 #14 的「聽力練習」，機制上是把任一題型的題幹從「顯示文字」改成「播放語音」。因此實作為 render 的一個選項：

```js
render(item, host, { present: 'audio' })
```

四個引擎都支援，等於一次得到四種聽力題型。使用者可在設定中選擇聽力題的比例。

### 6.3 單字循環播放（#15）是播放器，不是題目

獨立模組 `ui/player.js`。連續播放選定範圍的單字（日→停頓→中，或日→日），可設間隔與循環。

**選詞為依熟悉度加權的隨機抽樣，不是順序輪播。** 權重同排程器（§8.1 的 `W`），因此不熟的單字自然被更常播到，已經很熟的偶爾出現以維持記憶。使用者可調整「偏重生詞 ↔ 平均分布」的強度（即權重指數 α）。

**不產生複習事件。** 純聆聽沒有作答，無法評估掌握度；若計入會虛報熟悉度，反而讓排程器少考真正該考的字。播放器只**讀取** SRS 狀態，不寫入。

**已知風險**：iOS Safari 的 `speechSynthesis` 在螢幕鎖定或切換到背景時會被系統暫停，因此鎖屏播放無法用 TTS 達成。緩解：Phase 2 若此功能重要，改為預先產生 mp3 並以 `<audio>` 元素播放，搭配 Media Session API 支援鎖屏控制。第一版接受「須保持螢幕開啟」的限制，並在 UI 明示。

### 6.4 插畫（nice to have，Phase 4）

**來源為課本 PDF 內建的情境插畫**，非外部圖示集。課本每課附有大量線稿插畫（第 1 課即有 31 個影像物件），與課文情境直接對應，記憶連結遠強於通用 emoji；且使用者翻閱實體課本複習時看到的是同一張圖。智財權狀態與已抽取的文字相同（同一本書、同樣私有自用，站台維持私有）。

- 抽取：影像物件多為 FlateDecode 或 DCTDecode，連同其頁碼與頁面座標一併記錄（Phase 0 Task 14）。
- 關聯：`data/illustrations.json` 人工對應圖片與概念／句子，`{"L07-bunkei-2": "img/07-p03-02.png"}`（Phase 4）。
- 僅用於題目提示與單字瀏覽，不參與作答判定。缺圖者不顯示，不影響任何功能。

### 6.5 語言規則模組（`app/lang/`）

純函式、無 DOM 依賴、必須有測試。

- **`conjugation.js`**：`conjugate(verb, form)`。一次寫完整（含可能形、意向形、受身、使役、敬語），由 `requires_lesson` 控制何時解鎖，日後範圍擴大不需改程式。
  - **必須處理例外**：`帰ります`、`入ります`、`走ります`、`知ります`、`切ります` 等外形似 II 類實為 I 類的動詞。動詞分類存在 `data/verbs.json`，由抽取初判＋人工校對。
  - 各形態的 `introduced_in_lesson`：ます形 4、て形 14、ない形 17、辞書形 18、た形 19、可能形 27。
- **`adjective.js`**：い／な 形容詞的現在肯定否定、過去肯定否定、て形、副詞形。
- **`numbers.js`**：數字、時間、日期讀音，含不規則（`よじ` 非 `しじ`、`はつか` 非 `にじゅうにち`、`ついたち`、`ようか`）。
- **`counters.js`**：量詞音變（`いっぽん`／`さんぼん`／`ろっぽん`、`いっさつ`、`はっぴき`）。
- **`kana.js`**：假名正規化、平片假名互轉、羅馬字。

## 7. 熟悉度模型（近十次答對率）

> **設計沿革：** 本節原本採 FSRS-lite（S／D 狀態 ＋ `R(t) = (1 + t/(9S))^-1`）。
> 實際使用後廢止：R 的定義是「距上次複習 t 天後還記得的機率」，`t≈0` 時恆等於 1，
> 因此**剛練完的儀表板永遠顯示 100%**，答對答錯都一樣，使用者看不出任何資訊。
> 現改為下述的「近十次答對率」模型。事件日誌格式未變，舊事件可直接重放。

### 7.1 狀態

熟悉度 **A** 掛在**概念**上，不掛在題目上——這樣同一個詞在不同題型之間才能傳導
（見 §8 末段）。每個概念只維護兩個數字，沒有 S、沒有 D：

- **近十次作答結果**（只取最近 10 筆，先進先出）
- **reps** 累計作答次數

```
A = 最近 min(10, reps) 次作答中，答對的比例
reps = 0 的概念（從未考過）：A = 0
```

「答對」的判準是 §7.4 的 grade ≥ 2；grade = 1（答錯）記為未答對。grade 的四級刻度
保留不動，事件日誌照舊記錄，只是 A 的計算只看「對／錯」這個二元結果。

例：考過 5 次對 3 次 → A = 0.6。考過 20 次 → 只看最近 10 次，前 10 次不再影響。

### 7.2 A 不隨時間衰減（需求 #20 的歸屬）

**A 是答對率，不是記憶保留率，因此不打折。** 某個概念連對十次之後放著半年不碰，
A 仍是 100%——那是事實陳述：「我考這個概念的正確率是 100%」。

需求 #20「熟悉度隨時間打折」的目的是**久沒練的要多練**，這件事由 §8 的出題權重
`W` 裡的時間項完成，不由 A 承擔。把時間因素同時塞進 A 和 W 會讓儀表板上的數字
混合兩件事——使用者看到 60% 時無法分辨是「答錯過」還是「只是太久沒碰」。

**實作者注意：不要「修好」這件事。** 替 A 加上時間折扣看似更精緻，但那是本節明確
廢止的行為，會讓儀表板退回到無法解讀的狀態。

### 7.3 更新

一次作答更新該題 `covers` 的所有概念（歸因見 §7.5）：把本次的對／錯推入該概念的
近十次佇列（滿 10 筆則擠掉最舊一筆），`reps += 1`，並記錄**該題目**的作答時戳。

時戳記在**題目**上而不是概念上——§8 的時間項問的是「這一題多久沒出現了」。

### 7.4 grade 的自動判定

使用者不需手動評分（自評卡已從設計移除）：

| 條件 | grade |
|---|---|
| 答對，反應時間 < 該題型中位數 × 0.6 | 4 簡單 |
| 答對 | 3 普通 |
| 答對，但反應時間偏長或用過提示 | 2 困難 |
| 答錯 | 1 重來 |

A 只區分 grade ≥ 2（對）與 grade = 1（錯）。保留四級是為了日後分析與可能的演算法
調整——事件不可變，改演算法後重放歷史即可重算。

### 7.5 概念層的更新與歸因

一次作答同時更新該題 `covers` 的所有概念。歸因策略：

1. **單一考點題**（transform、cloze 的助詞題）：答錯歸因明確，全額計入該概念。
2. **複合題**（substitute）：所有 covered concepts 一律計入。在二元對錯的模型下無法
   均攤權重，因此複合題答錯會讓所有考點都記一次錯——這是已知的過度歸因，代價是
   代入題答錯時助詞與句型概念一起被拉低。
3. **Phase 4 精準歸因**：對 substitute 的作答與正解做 token 級 diff，錯在助詞位置就
   只歸咎助詞概念，錯在動詞語尾就只歸咎變化規則。技術可行，但不應擋住第一版。

### 7.6 技能分類（需求 #19 的呈現面）

技能是**儀表板的分組維度**，不是排程的驅動力。共六類，由概念 ID 前綴決定歸屬：

| 技能 | 概念類型 | 內容 |
|---|---|---|
| **單字** | `w:<lemma>` | 詞義（中↔日） |
| **讀音** | `w:<lemma>:reading` | 漢字的假名讀法 |
| **變化** | `r:<form>:<group>`、`w:<lemma>:group` | 動詞／形容詞變化規則、動詞分類 |
| **助詞** | `p:<particle>:<usage>` | 助詞用法 |
| **句型** | `g:<pattern>` | 文法句型 |
| **數量** | `c:<counter>`、`n:<type>` | 量詞、數字、時間、日期 |

```
技能熟悉度 = 該技能底下「複習範圍內」所有概念的 A 之算術平均
```

**兩個關鍵，都是為了讓這個數字能讀：**

1. **未考過的概念以 A = 0 計入分母**，不是排除在外。排除的話，練完 20 題就只在這
   20 個剛答對的概念上取平均，必然接近滿分。計入之後數字從 0% 開始長，反映的是
   真實進度。
2. **算術平均，不加 `log(1 + reps)` 權重。** 原本加權是為了「避免只練過一次的概念
   左右大局」，但在 A = 0 也計入分母的前提下，權重會讓未考過的概念（reps = 0 →
   權重 0）再次被排除，直接抵銷第 1 點。

儀表板必須同時顯示**分母與已練數**（例：`單字 41%　已練 120 / 749`）。只給百分比
的話，41% 是「120 題都很熟但只練了一小部分」還是「749 題都練過但都不熟」無法分辨。

**每答完一題即重畫，不是只在開新一輪時畫一次。** 練到一半看儀表板卻完全不動，使用者
無從分辨「數字沒變」與「功能壞了」——實測中這正是第一個被誤認為 bug 的行為。

**分母隨複習範圍變動**（需求 #17 的副作用）：範圍設 1 ~ 15 課時單字的分母是七百多，
一天練 20 題百分比只動 1 ~ 2%；縮到 1 ~ 3 課分母剩一百多，數字立刻有感。這是刻意的
——分母代表「我替自己設定的這個範圍」，不是整本書。

**「聽力」是橫切面，不是第七類技能。** 聽力沒有專屬的概念——聽 `おくります` 考的
仍是 `w:okurimasu` 這個概念，只是換了呈現方式。因此聽力熟悉度由**事件的 `m` 欄位**
（作答模式）聚合而得：取所有 `m = 'audio'` 的事件計算表現，與上述六類並列顯示，但
屬於不同維度。這也讓儀表板能回答「同一批單字，我用看的比用聽的熟多少」。

## 8. 排程器

```
候選 = items 且 requires_lesson ≤ scope.maxLesson
             且 lesson ∈ scope.lessons
             且 engine ∈ scope.enabledEngines
             且 skills ∩ scope.skills ≠ ∅
```

### 8.1 出題權重

```
W(item) = (1 - A_item) + f(ΔT_item)

A_item  = min over c ∈ item.covers 之 A_c        最弱環節
f(ΔT)   = ΔT / (ΔT + k)                          k = 7 天（預設，可調）
ΔT      = 距該題目上次被出的天數；從未出過則 f = 0
```

兩項各自落在 0 ~ 1，故 `W ∈ [0, 2]`。兩個要求都成立：**A 愈低 W 愈高**（第一項），
**愈久沒考 W 愈高**（第二項）。

`f(ΔT)` 的刻度（k = 7）：

| ΔT | 1 天 | 3 天 | 7 天 | 14 天 | 30 天 |
|---|---|---|---|---|---|
| f | 0.13 | 0.30 | 0.50 | 0.67 | 0.81 |

代表情境：

| 情境 | A | ΔT | W | 桶 |
|---|---|---|---|---|
| 不熟又很久沒考 | 0.0 | 30 天 | 1.81 | 高 |
| 從未考過 | 0.0 | — | 1.00 | 高 |
| 不熟但剛考過 | 0.0 | 今天 | 1.00 | 高 |
| 半生不熟、一週沒碰 | 0.5 | 7 天 | 1.00 | 高 |
| 熟但很久沒考 | 1.0 | 30 天 | 0.81 | 中 |
| 熟又剛考過 | 1.0 | 今天 | 0.00 | 低 |

**`A_item` 取 min 而非平均**，是為了讓「這題考到的任何一個弱概念」都足以把它拉上來。
一道變化題同時考 `r:te:I` 與 `w:送ります:group`，只要其中一個不熟就該練。

### 8.2 分桶與抽樣

```
高：W ≥ 1.0        中：0.4 ≤ W < 1.0        低：W < 0.4
```

- **只從「高」與「中」兩桶出題**，桶內以 W 為權重隨機抽樣（不是排序取前 N——純排序
  會讓每次練習都是同幾題，使用者會背下順序而非內容）。
- **若高 ＋ 中的題數不足本次所需**（範圍內全部練熟且剛練過時會發生），才把「低」桶
  一併納入。否則會回傳不足額的題數。
- 本 session 已出現過的題目，W 乘上 0.05 強力衰減，避免同一輪重複。
- 答錯的題目在 3 ~ 5 題後重新插入（lapse re-drill）。
- 新題比例上限 30%／session，避免一次灌入過多生題。從未考過的題目 W = 1.00 落在
  「高」桶，沒有這個上限會讓生題灌滿整輪。

### 8.3 需求 #19 如何成立

A 掛在概念上而非題目上，因此熟悉度跨題型傳導：某單字常答錯 → 該概念 A 低 →
所有 `covers` 含它的題目（中譯日、漢字讀音、聽力）W 一起升高，即使其中某些題型
**從未出現過**。某文法常錯 → 使用該文法的所有題型一起升高。

`k = 7` 與分桶切點（1.0 / 0.4）是預設值，不是推導所得。實際使用後若「太常重複」或
「太久才輪到」，調這三個數字即可，不需改動模型。

## 9. 作答與評分

**輸入方式：僅打字模式。**（已確認不做詞塊拼裝與內建假名鍵盤。）輸入框設定 `lang="ja"`、`autocorrect=off`、`autocapitalize=off`、`spellcheck=false`。

### 9.1 正規化規則

原則：**格式差異一律寬鬆，語言本身的差異一律嚴格。**

| 情況 | 處理 |
|---|---|
| 空白（課本用全形空格分詞） | 移除所有空白後比對 |
| 漢字 vs 假名（`食べます`／`たべます`） | 兩者皆正確，除非該題考點即為漢字寫法 |
| 句號 `。`／`.`／未輸入 | 皆正確 |
| 全形／半形數字、英文 | 皆正確 |
| 長音、促音、濁音（`きって`／`きて`、`ビール`／`ビル`） | **必須正確**，此為考點 |

### 9.2 答案不唯一的處理

移除中翻日之後，答案仍然不是唯一的。四種來源，以四層防線處理，前三層自動、第四層才由使用者介入：

| 來源 | 例 | 處理層級 |
|---|---|---|
| 課本自己標註的替代形 | 第7課文型3 `もらいました。（から）` → `に`／`から` 皆可 | **抽取時**存入 `sentence.alt` |
| 助詞的合法替代 | `日本へ 行きます`／`日本に 行きます` | **生成時**依規則列舉（方向 `へ`↔`に`、對象 `に`↔`から`） |
| 中文釋義撞詞 | 「知道」對應 `わかります` 與 `知っています` | **生成時**偵測：同範圍內某中文釋義對應多個日文詞，則互列為 alternatives |
| **語序自由度** | `木村さんに 花を あげます`／`花を 木村さんに あげます` | **無法窮舉**（隨補語數量階乘成長）→ 由 §9.2.1 處理 |

前三類必須在生成階段解決，目標是讓第四類的殘留頻率夠低。

### 9.2.1 「我這樣寫也對」（安全網）

答錯時顯示正解，旁附此按鈕。按下後補記**一筆**事件：`g = 3`（本次判定改為答對）
且 `a = 使用者輸入的寫法`（見 §10.1）。這一筆同時完成兩件事——修正 SRS 的錯誤歸因，
以及讓該寫法成為該題的 alternative，下次同樣寫法自動判對。

寫入必須 `await` 完成。不 await 的話，使用者按完立刻關閉分頁就可能整筆遺失，而這個
按鈕存在的理由正是「不讓誤判污染排程」——靜默掉一筆修正等於這個安全網沒作用。

**保留此機制的理由是資料正確性，不是使用者體驗。** 一個正確答案被判錯，損害不止於當下：該筆事件進入 SRS 後，系統會判定使用者不熟這個概念，於是**提高該題的出題機率**——誤判會讓排程器往完全相反的方向加強。未修正的誤判會持續污染學習排程，這比單純答錯一題嚴重得多，因此值得保留一個逃生口。

**存放位置與 `data/corrections.json` 分開**：`data/corrections.json` 是開發期人工校對抽取錯誤用的靜態檔，隨網站部署；使用者按此按鈕產生的是**使用者資料**，與事件日誌存在同一個 Store、走同一套同步機制。兩者在載入時合併套用，使用者層優先。

**已知取捨**：使用者可能手滑把真正的錯誤標成對的。單一自學使用者情境下風險可接受；儀表板會列出「已加入的自訂答案」供隨時檢視移除。

### 9.3 振假名顯示（需求 #16）

**預設一律顯示，不需使用者按按鈕。** 假名置於漢字**上方**，與課本排版一致（已由 `tools/render.swift` 算繪確認：課本的 `お上がり` 之 `あ`、`失礼` 之 `しつれい` 皆在漢字上方，為標準日文 ruby 排版）。

```css
ruby { ruby-position: over; }   /* 瀏覽器預設值，無須前綴 */
```

```html
<ruby>手紙<rt>てがみ</rt></ruby>を <ruby>書<rt>か</rt></ruby>きます
```

**唯一的例外是考讀音的題型**（`recall` 的「漢字→假名」），該題型的題幹必須隱藏 `<rt>`，否則答案直接寫在題目上。此判斷由題目的 `covers` 是否含 `w:*:reading` 決定，不由使用者設定控制——避免使用者誤開設定後題目失效。

答案揭曉、複習與單字瀏覽畫面則一律顯示。

### 9.4 出處（需求 #17）

每題顯示 `source_ref` 文字，如「第 7 課 練習Ｂ-3」。**不提供 PDF 連結或內嵌**（見 §12）。

## 10. 儲存與同步

### 10.1 事件日誌

```js
{ d: 'a3f9', n: 1482, i: 'conj:okurimasu:masu→te', t: 1757500000, g: 3, r: 2400, m: 'text' }
```

短鍵以節省空間。每筆約 50 bytes；一年 2 萬題約 1 MB。

**選用欄位 `a`——使用者按下「我這樣寫也對」時記錄的寫法：**

```js
{ d: 'a3f9', n: 1483, i: 'conj:okurimasu:masu→te', t: 1757500004, g: 3, r: 0, m: 'text',
  a: '送って' }
```

`a` 只出現在「我這樣寫也對」產生的那一筆補記事件上，其餘事件沒有這個欄位。舊事件
缺少 `a` 是合法的，重放時略過即可。**`(d, n)` 主鍵與合併規則完全不變。**

這是 §9.2.1 所要求的「與事件日誌存在同一個 Store」的落實方式：使用者認可的寫法本身
就是事件的一部分，重放事件即可重建每題的自訂 alternatives。**不得改存 localStorage**
——localStorage 不在 `allEvents()` 的輸出裡，會導致 `exportJSON()` 漏掉這些寫法，且
Phase 3 的同步完全帶不過去（在 Mac 上認可的寫法，手機不會知道）。

`d` 為裝置 ID（首次使用時隨機產生一次並存於本機），`n` 為該裝置的單調遞增序號。**`(d, n)` 即事件的全域唯一鍵**，多裝置合併時據此去重。不可用 `(i, t)` 當鍵——時戳只到秒，理論上會碰撞，且無法區分「同一題連續作答兩次」與「重複的同一筆事件」。

**只儲存事件，不儲存 S/D/R。** 三個理由：

1. 演算法或權重調整後可重放全部歷史，過往紀錄不會歸零。
2. 多裝置合併 = 取聯集。事件不可變，合併後排序重算，永不衝突。
3. 支援學習分析（哪一課的助詞特別弱、什麼時段答對率高）。

派生狀態以快照快取於 IndexedDB，鍵為事件數與最後時戳；事件量大時只重放快照之後的部分。

### 10.2 儲存 Adapter

```js
// app/core/store.js
export interface Store {
  appendEvents(events): Promise<void>
  allEvents(): Promise<Event[]>
  sync(): Promise<{pulled, pushed}>     // LocalStore 為 no-op
}
```

- **Phase 1 `LocalStore`**：IndexedDB。附手動匯出／匯入 JSON。
- **Phase 3 `GiteaStore`**：包裝 LocalStore，額外做遠端合併。

### 10.3 Gitea 同步（Phase 3）

- private repo，單一檔案 `progress.json`。
- 讀：`GET /api/v1/repos/{owner}/{repo}/contents/progress.json` → base64 解碼 → 取得內容與 `sha`。
- 寫：`PUT` 同路徑，帶上讀到的 `sha`。**`sha` 即樂觀鎖**——若另一裝置已寫入，此次寫入被拒，程式重新拉取、合併、重試（上限 3 次）。
- 合併：事件以 `(i, t)` 去重取聯集，依 `t` 排序。因事件不可變，此合併無資料遺失風險。
- 認證：personal access token，權限只勾該 repo 讀寫，存於 IndexedDB，**不進版控、不寫死在程式中**。
- 觸發時機：session 結束、頁面隱藏（`visibilitychange`）、手動按鈕。離線時累積於本地，恢復連線後補送。

**前置條件（待使用者確認）**：

1. Gitea 須為 HTTPS（網站若為 https，fetch http 端點會被瀏覽器擋為 mixed content）。
2. 若網站與 Gitea 不同網域，Gitea `app.ini` 須設 `[cors] ENABLED = true`；**若網站也託管於同一 Gitea 網域則無此問題**。
3. 手機在外網須連得到 Gitea。若僅限區域網路，功能仍可用，但出門的紀錄會延遲到回家才同步。

### 10.4 網站託管

純靜態站，換位置成本為零，因此**刻意不在設計階段綁定**：

- 開發期：`python3 -m http.server`，手機連同一 Wi-Fi 測試。
- 若 Gitea 對外可達：託管於 Gitea（同網域、零 CORS、全自主）。
- 若 Gitea 僅限 LAN：託管於 Cloudflare Pages，並於 Gitea 開啟 CORS。

#### 實作決定（2026-09-23 定案，偏離本文件前述段落之處）

1. **`app/engines/` 延到 2b 才建。** §11 列了 `generators/` 與 `engines/` 兩層，但 Phase 1 只做了前者——所有題目共用 `ui/session.js` 的單一文字輸入畫面，評分統一走 `core/grading.js`。2a 的 substitute 與 cloze 仍然都是打字作答，塞得進現有的 `prompt`／`answer`／`alternatives` 形狀，此時建 engines/ 只是多一層沒有行為差異的轉接。真正需要獨立 render 的是 2b 的 `jp2zh` 選擇題，屆時這層才有分歧可承載。

2. **`concepts.json` 不收 `skills` 欄位。** §5.2 的範例寫了 `"skills": ["文法", "助詞"]`，但 §7.6 規定技能由概念 ID 前綴決定，且 `core/concepts.js` 的 `skillOf()` 已如此實作。兩者並存會造成兩個真相來源而無仲裁規則，且範例中的「文法」不屬於 §7.6 的六類技能，照抄會讓該概念落不進任何一條長條圖。`concepts.json` 只收 `label`／`requires_lesson`／`source_ref`；技能一律由前綴推導。

3. **數量題不新增第五個引擎。** §6.1 明定四個引擎，數字與量詞歸在 recall。使用者仍需單獨開關數量題，此需求由排程器既有的 `skills ∩ scope.skills ≠ ∅`（§8）承擔：`generators/quantity.js` 產出 `engine: 'recall'` 但 `skills: ['數量']` 的題目，分檔清楚而引擎數不變。

4. **`concepts.json` 增設 `patterns` 反查表。** substitute 的 `covers` 需要知道每張練習Ａ代入表考的是哪個文法概念，而 78 張表與 91 則文法非 1:1，資料中亦無此對應，只能人工建立。存於概念定義內（`"patterns": ["L07-A1"]`）而非另立第四個資料檔。

5. **練習Ｂ（`drills[]`）納入 substitute 素材。** 實測 107 則中 72% 完整可用（`items`、`model_answer`、`model_cue` 齊備），27% 不可用者集中於第 1 ~ 3 課且 `items` 為空——屬 Phase 0 抽取缺口，不在 2a 修補，該等條目自然不產題。

6. **手維護資料檔須有漂移偵測測試。** `particles.json` 的每筆 `at` 位置必須在對應句子中確實是所標的助詞；`particles.json`／`concepts.json` 的概念引用不得懸空；`concepts.json` 的 `patterns` 條目須對得上實際 pattern id；`adjectives.json` 的鍵須在 vocab 中存在。課本語料若重新抽取而位移，測試必須紅燈而非靜默錯位——與 Phase 0 的不變式檢查同一套思路。
